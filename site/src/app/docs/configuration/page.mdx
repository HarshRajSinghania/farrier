# Configuration

Farrier is configured with plain files in its data directory and a few environment variables. There is no configuration in the database, so a deployment is reproducible from a directory and a secret.

## Data directory

Set with `--data` or `FARRIER_DATA`. Defaults to `./farrier-data`, or `./farrier-demo` for `farrier demo`.

```
farrier-data/
├── farrier.db                     # SQLite: endpoints, observations, renewals, events
├── master.key                   # Fernet key sealing private keys (unless FARRIER_MASTER_KEY is set)
├── issuers.json                 # which CAs to use (optional)
├── settings.json                # planner tuning (optional)
├── acme-account-<hash>.key      # one ACME account key per directory URL
├── local-ca/                    # built-in private CA (ca.key, ca.pem)
└── packs/<renewal-id>/          # manual change packs, deleted once verified
```

<Callout type="danger" title="Back up master.key">
Without `master.key` (or `FARRIER_MASTER_KEY`), the sealed private keys in `farrier.db` can't be decrypted. Back up both together.
</Callout>

## Issuers: `issuers.json`

Maps issuer names to CAs. Endpoints choose one with their `issuer` field. If an endpoint names an issuer that doesn't exist, `default` is used. Without the file, Farrier uses only the built-in private CA:

```json
{ "default": { "type": "local_ca" } }
```

Any string value can be a secret reference (`env:NAME` or `file:/path`).

### Let's Encrypt

```json
{
  "default": { "type": "local_ca" },
  "le": {
    "type": "acme",
    "directory_url": "https://acme-v02.api.letsencrypt.org/directory",
    "email": "pki@example.com",
    "dns_hook": "/opt/farrier/hooks/route53.sh",
    "propagation_seconds": 60
  }
}
```

### Commercial CA with External Account Binding

DigiCert, Sectigo, Entrust and others expose ACME with EAB credentials:

```json
{
  "digicert": {
    "type": "acme",
    "directory_url": "https://acme.digicert.com/v2/acme/directory/",
    "eab_kid": "env:DIGICERT_EAB_KID",
    "eab_hmac_key": "env:DIGICERT_EAB_HMAC",
    "dns_hook": "/opt/farrier/hooks/infoblox.sh"
  }
}
```

### AWS Certificate Manager (managed ACME)

ACM can run an ACME server for you: each **endpoint** has its own directory URL, a list of **domains** it may
issue for, and **External Account Bindings** (EAB) that authorize clients. Domains are validated once, up front,
through a CNAME, so Farrier needs no DNS access at issuance time. ACM certificates last 45 days; Farrier renews
them like any other.

The `farrier acm` commands use the standard AWS credential chain (environment keys, IRSA, ECS/EKS task role,
EC2 instance profile). Run them as a PKI administrator.

**1. Create an endpoint** (one per authorization boundary, e.g. per environment):

```bash
farrier acm --region eu-west-1 endpoint create --key-types ec256,rsa2048 --wait
# endpoint:  arn:aws:acm:eu-west-1:123456789012:acme-endpoint/abcd...
# directory: https://acm-acme-enroll.eu-west-1.api.aws/abcd.../directory
```

**2. Allow your domains.** With `--hosted-zone-id`, ACM writes the CNAME in Route 53 itself. Without it,
the command prints the CNAME to create at your DNS provider. Keep that record: it authorizes every renewal.

```bash
farrier acm domain add <endpoint-arn> example.com --hosted-zone-id Z0123456789ABC --wildcards --wait
farrier acm domain list <endpoint-arn>
```

**3. Create an External Account Binding.** It names the IAM role ACM assumes when it issues. That role
trusts `acm-acme.amazonaws.com` (with `sts:AssumeRole`, `sts:TagSession`, `sts:SetSourceIdentity`) and
may `acm:RequestCertificate` and `acm:RevokeCertificate` (plus `acm:AddTagsToCertificate` if the endpoint
tags certificates). Creating the binding needs `iam:PassRole` on it.

```bash
farrier acm eab create <endpoint-arn> --role-arn arn:aws:iam::123456789012:role/acme-issuer --expires-days 365
```

**4. Add the issuer.** On AWS (ECS, EKS, EC2), give the engine's role `acm:DescribeAcmeEndpoint` and
`acm:GetAcmeExternalAccountBindingCredentials` (the Terraform modules do this when you set
`acm_acme_endpoint_arns`) and point the issuer at the binding. Farrier reads the directory URL and the
EAB key from ACM, so no secret is stored:

```json
{
  "acm": { "preset": "aws-acm", "acm_eab_arn": "arn:aws:acm:eu-west-1:123456789012:acme-endpoint/abcd/acme-external-account-binding/ef01" }
}
```

Running outside AWS (GKE, AKS, on premises)? Print the credentials once with
`farrier acm eab credentials <binding-arn>`, store them in your secret store, and use the portable form,
which the dashboard's **AWS Certificate Manager (ACME)** preset also writes:

```json
{
  "acm": {
    "preset": "aws-acm",
    "directory_url": "https://acm-acme-enroll.eu-west-1.api.aws/abcd/directory",
    "eab_kid": "env:ACM_EAB_KID",
    "eab_hmac_key": "env:ACM_EAB_HMAC"
  }
}
```

Endpoints then use `"issuer": "acm"`. A name outside the endpoint's domains fails with
"not prevalidated on this ACME endpoint"; add the domain with step 2. Other ACME clients (cert-manager,
Certbot) can use the same endpoint with the credentials from `farrier acm eab credentials`.

Housekeeping: `farrier acm eab revoke` stops new registrations with a binding (existing accounts keep
working), `farrier acm domain delete` stops issuance for a domain, and `farrier acm endpoint delete` removes
the endpoint with its domains and bindings. Certificates already issued stay valid. Every command takes
`--json`.

### Cloud private CAs: AWS Private CA and Google CAS

For internal names, Farrier can use your cloud's private CA. There is no DNS validation: the cloud IAM policy
on the CA decides who may issue. Credentials come from the platform (IRSA, ECS/EKS task role, instance profile,
GKE workload identity, the metadata server) or the usual `AWS_*` / `GOOGLE_APPLICATION_CREDENTIALS` variables.

```json
{
  "internal-aws": {
    "type": "aws_pca",
    "ca_arn": "arn:aws:acm-pca:eu-west-1:123456789012:certificate-authority/1a2b3c4d-...",
    "template_arn": "arn:aws:acm-pca:::template/EndEntityCertificate/V1",
    "lifetime_days": 30
  },
  "internal-gcp": {
    "type": "gcp_cas",
    "ca_pool": "projects/my-project/locations/europe-west1/caPools/internal",
    "certificate_template": "projects/my-project/locations/europe-west1/certificateTemplates/tls-server",
    "lifetime_days": 30
  }
}
```

| Key | Notes |
| --- | --- |
| `ca_arn` | `aws_pca`: the CA, in this account or shared from another through AWS RAM |
| `template_arn`, `signing_algorithm` | `aws_pca`, optional: the algorithm defaults to the one matching the CA's key |
| `ca_pool`, `certificate_template`, `issuing_ca` | `gcp_cas`: the pool, an optional template, and an optional CA within the pool |
| `lifetime_days` | Defaults to the public maximum for today, to rehearse the 47-day schedule; set your PKI's value |

Permissions: `acm-pca:IssueCertificate`, `acm-pca:GetCertificate` and `acm-pca:DescribeCertificateAuthority`
on the CA; on Google, `roles/privateca.certificateRequester` on the pool (plus `privateca.caPools.get` for the
dashboard's **Test** button). Clients must trust the CA's root.

### `acme` options

| Key | Default | Notes |
| --- | --- | --- |
| `directory_url` | Let's Encrypt **staging** | Set explicitly for production |
| `email` | none | Account contact |
| `dns_hook` | required | Shell command, see below |
| `propagation_seconds` | `60` | Wait after publishing TXT records |
| `eab_kid`, `eab_hmac_key` | none | External Account Binding |
| `acm_eab_arn` | none | `aws-acm` only: read the directory URL and EAB key from ACM |
| `poll_interval` | `2.0` | Seconds between order polls |
| `timeout` | `600` | Seconds before giving up on an order |

Only the DNS-01 challenge is supported, by design: the device never needs to be reachable from the CA.

### `local_ca` options

| Key | Default | Notes |
| --- | --- | --- |
| `name` | `Farrier Local CA` | CA subject |
| `lifetime_days` | public maximum for today | Override, e.g. `30` for a stress test |
| `simulate_date` | none | Issue as if on this date |

The private CA follows the public lifetime schedule by default, so you can rehearse the 47-day world today. Use it for labs and internal-only names; clients must trust `local-ca/ca.pem`.

## DNS-01 hook contract

`dns_hook` is run through the shell once per challenge, with these environment variables:

| Variable | Value |
| --- | --- |
| `FARRIER_DNS_ACTION` | `present` or `cleanup` |
| `FARRIER_DNS_NAME` | e.g. `_acme-challenge.vpn.example.com` |
| `FARRIER_DNS_VALUE` | the TXT value |

`present` must **add** a TXT value, not replace the record: a certificate for `example.com` and `*.example.com` needs two values on the same name. `cleanup` removes only the given value. A non-zero exit fails the issuance attempt, which is retried on the next tick. Each call has a 300-second timeout.

Example for BIND or any RFC 2136 server (`examples/dns-hook-nsupdate.sh`):

```sh
#!/bin/sh
set -eu
SERVER="${NSUPDATE_SERVER:-ns1.example.com}"
KEY="${NSUPDATE_KEY:-/etc/farrier/tsig.key}"
case "$FARRIER_DNS_ACTION" in
  present) OP="update add $FARRIER_DNS_NAME. 60 IN TXT \"$FARRIER_DNS_VALUE\"" ;;
  cleanup) OP="update delete $FARRIER_DNS_NAME. IN TXT \"$FARRIER_DNS_VALUE\"" ;;
  *) echo "unknown action $FARRIER_DNS_ACTION" >&2; exit 2 ;;
esac
printf 'server %s\n%s\nsend\n' "$SERVER" "$OP" | nsupdate -k "$KEY"
```

Write equivalents for Route 53, Infoblox or Azure DNS with their CLIs.

## Planner settings: `settings.json`

All keys are optional; missing keys use these defaults.

```json
{
  "horizon_days": 14,
  "manual_daily_cap": 25,
  "auto_daily_cap": 1000,
  "verify_max_attempts": 6,
  "verify_retry_seconds": 2.0,
  "issue_max_attempts": 5,
  "safety_days": 2,
  "scan_timeout": 5.0,
  "crypto_scan_hours": 24,
  "ssh_scan_hours": 24,
  "ssh_collect_hours": 24,
  "export_key_retention_hours": 24
}
```

| Key | Meaning |
| --- | --- |
| `horizon_days` | Create renewals this many days ahead of their due date |
| `manual_daily_cap` | Max manual renewals scheduled per day; excess spills to the next window |
| `auto_daily_cap` | Same, for automated renewals |
| `verify_max_attempts` | Ticks in `verifying` before an automated deploy is rolled back |
| `verify_retry_seconds` | Pause between the three handshakes within one verify attempt |
| `issue_max_attempts` | Issuance attempts before a renewal is marked `failed` |
| `safety_days` | A renewal's deadline is expiry minus this |
| `scan_timeout` | Seconds per TLS handshake during the tick scan |
| `crypto_scan_hours` | Hours between TLS crypto / PQC re-probes of each reachable endpoint (default `24`, `0` = off; [PQC](/docs/pqc)) |
| `ssh_scan_hours` | Hours between unauthenticated SSH host-key scans (default `24`, `0` = off; [SSH](/docs/ssh)) |
| `ssh_collect_hours` | Hours between `authorized_keys` collections over SSH (default `24`, `0` = off) |
| `export_key_retention_hours` | Hours an exported private key (endpoint tag `export-key`) stays in the cloud secret backend before Farrier deletes it (default `24`; [Events](/docs/events#security-model)) |

See [Concepts](/docs/concepts) for how these interact.

## Notifications

Add `notifiers` to `settings.json` to hear about renewals in Slack, Microsoft Teams or any webhook:

```json
{
  "dashboard_url": "https://farrier.example.internal/dashboard",
  "notifiers": [
    { "type": "slack", "url": "env:FARRIER_SECRET_SLACK_WEBHOOK" },
    { "type": "teams", "url": "file:/run/secrets/farrier/teams-webhook", "events": ["failed", "rolled_back"] },
    { "type": "webhook", "url": "https://hooks.example.internal/farrier",
      "headers": { "Authorization": "env:FARRIER_SECRET_HOOK_TOKEN" },
      "events": ["done", "failed", "rolled_back", "awaiting_manual"] }
  ]
}
```

- `events` defaults to `failed`, `rolled_back` and `awaiting_manual` (event-bus channels `eventbridge`, `pubsub` and `eventgrid`: `issued`, `awaiting_manual`, `done`, `failed`, `rolled_back` and `cancelled`; see [Events](/docs/events#transports)). Others: `planned`, `issued`, `verifying`, `done`, `superseded`, `cancelled`.
- `webhook` posts JSON: `event`, `endpoint`, `host`, `port`, `connector`, `owner`, `renewal_id`, `error`, `ticket`, `new_not_after`, `at`, `dashboard_url`. `slack` and `teams` post a one-paragraph `text` message.
- URLs and header values go through the secret guardrails, are resolved at send time and are never logged. Delivery runs in the background with a 5 second timeout; a failure is written to the event log and never blocks a renewal.
- Check the setup with `POST /api/notifiers/test`.

## Inventory: `farrier import`

Declare endpoints and their connectors in a JSON array and import them. Importing is an upsert by `name`, and each connector config is validated first.

```json
[
  {
    "name": "vpn-fgt",
    "host": "vpn.example.com",
    "port": 443,
    "issuer": "le",
    "connector": "fortigate",
    "connector_config": {
      "url": "https://fgt-mgmt.example.com",
      "api_token": "env:FGT_TOKEN",
      "bind": "sslvpn"
    },
    "window": { "days": ["sat"], "start": "02:00", "hours": 4 },
    "owner": "network"
  }
]
```

| Field | Default | Notes |
| --- | --- | --- |
| `name` | required | Unique |
| `host` | required | Hostname or IP to connect to |
| `port` | `443` | |
| `sni` | none | Server name to send; defaults to `host` when it is a hostname |
| `common_name` | from the observed cert, else `host` | CN of the new certificate |
| `sans` | from the observed cert | Additional names |
| `key_type` | `ec256` | `ec256`, `ec384`, `rsa2048`, `rsa3072`, `rsa4096` |
| `connector` | `manual` | See [Connectors](/docs/connectors) |
| `connector_config` | `{}` | Connector-specific |
| `issuer` | `default` | Key in `issuers.json` |
| `window` | `{}` (any time) | UTC change window |
| `lead_days` | `0` | Minimum days before expiry to start |
| `owner`, `tags` | none | For filtering and reporting |
| `enabled` | `true` | Disabled endpoints aren't scanned or renewed |

`examples/inventory.json` has a complete example covering F5, FortiGate, PAN-OS, a Java keystore and a manual ASA with a ServiceNow ticket.

## Environment variables

| Variable | Used by | Purpose |
| --- | --- | --- |
| `FARRIER_DATA` | CLI | Data directory (overridden by `--data`) |
| `FARRIER_API_TOKEN` | `farrier serve` | Admin bearer token: read and change. Mandatory for a non-loopback bind |
| `FARRIER_API_READ_TOKEN` | `farrier serve` | Optional read-only token: every `GET`, including `/metrics`; anything else gets `403` |
| `FARRIER_MASTER_KEY` | engine | Fernet key for sealing private keys; overrides `master.key` |
| `FARRIER_ALLOW_API_COMMANDS` | API | `1` lets `POST /api/endpoints` accept `test_command`, `reload_command`, `ssh` and `dns_hook`. Off by default |
| `FARRIER_SECRET_ENV_PREFIX` | connectors, issuers, notifiers | If set, `env:` references must start with it (e.g. `FARRIER_SECRET_`) |
| `FARRIER_SECRET_DIRS` | connectors, issuers, notifiers | If set, `file:` references must sit under one of these directories (`:`-separated, `;` on Windows) |
| `FARRIER_DASHBOARD_URL` | notifiers | Link added to notifications (or `dashboard_url` in `settings.json`) |
| `FARRIER_SECRET_BACKEND` and `FARRIER_SECRET_*` | engine | Where dashboard-entered secrets live: `local` (default), `aws`, `gcp`, `azure`, `hashicorp`; per-backend settings in [Enterprise deployment](/docs/enterprise#engine) |
| `FARRIER_SECRET_EXTERNAL_PREFIXES` | connectors, issuers, notifiers | Comma-separated prefixes `aws-sm:`, `gcp-sm:`, `azure-kv:`, `hcvault:` references must start with. Unset: only the configured backend's own location and prefix |
| `FARRIER_MASTER_KEY_KMS` | engine | `FARRIER_MASTER_KEY` is wrapped; unwrap it at boot with this key (`aws-kms:`, `gcp-kms:`, `azure-kv:`) |
| `FARRIER_STORAGE_URL` and `FARRIER_STORAGE_*` | engine | Object store for change packs, chains, backups and audit exports (default: `objects/` in the data directory); see [Enterprise deployment](/docs/enterprise#engine) |
| `FARRIER_INSTANCE_ID` | events | CloudEvent `source` becomes `farrier://<id>` (`A-Z a-z 0-9 . _ ~ -`). Default: `farrier-` plus a hash of the master key, the same on every replica |
| `FARRIER_TRUSTED_PROXY_HOPS` | web | Proxies in front of the dashboard that append to `X-Forwarded-For`; the client address is that many entries from the right (default `1`, `0` = ignore the header). See [Security](/docs/security#behind-proxies) |
| `FARRIER_DOCS_URL` | web | Where the dashboard's documentation links go, read at runtime, e.g. your own copy of these docs. Default: the public docs site the image was built for, else the docs' source on GitHub |
| any `NAME` referenced as `env:NAME` | connectors, issuers, notifiers | Secrets. `FARRIER_MASTER_KEY` and the API tokens can never be referenced |

The web dashboard has its own variables; see [Self-hosting](/docs/self-hosting#dashboard-environment).

## CLI

Global option: `--data PATH`.

| Command | What it does |
| --- | --- |
| `farrier serve [--host 127.0.0.1] [--port 8740] [--tick 300]` | REST API (OpenAPI docs at `/docs`) and background renewal loop |
| `farrier demo [--port 8740] [--tick 20] [--simulate-date YYYY-MM-DD]` | Simulated estate on localhost |
| `farrier scan TARGETS… [--register] [--timeout 3] [-v]` | Report what certificates targets serve; `--register` adds unknown ones as manual endpoints |
| `farrier import FILE` | Upsert endpoints from a JSON inventory |
| `farrier tick` | Run one scan/plan/advance cycle and print the result |
| `farrier forecast [--certs 1000] [--manual 0.4] [--minutes 45] [--lead 0]` | Renewal workload under the CA/B Forum schedule |
| `farrier backup --to URL` | Export the database, HMAC-signed with a key derived from the master key, to `backups/` under an object-storage URL |
| `farrier restore --from URL [--to DB] [--allow-unsigned]` | Load a backup into an empty database. Refuses a missing or wrong signature; `--allow-unsigned` only for trusted backups made before signing |

### Target syntax

Used by `farrier scan` and the Discovery screen. Items are separated by spaces or commas.

| Form | Example |
| --- | --- |
| host (port 443) | `vpn.example.com` |
| host:port | `jira.example.com:8443` |
| CIDR with several ports (separated by a pipe) | <code>10.20.0.0/22:443&#124;8443&#124;4443</code> |
| connect to an IP, send an SNI | `www.example.com@10.20.1.10:443` |

Hostnames, ports and ranges are validated, and malformed targets are rejected rather than scanned. A single range may not exceed 65,536 addresses, and the API accepts at most 4,096 targets per request.
