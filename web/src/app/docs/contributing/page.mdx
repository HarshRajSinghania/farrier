# Contributing

Farrier is MIT-licensed and contributions are welcome: connectors for more devices, fixes, docs and UI. This page covers how the repository is laid out and what a good pull request looks like.

## Repository layout

```
farrier/                      Python engine (package "farrier")
├── api.py                  FastAPI app: REST API + background tick loop
├── cli.py                  `farrier` command
├── engine.py               renewal state machine (plan / advance / tick)
├── policy.py               CA/B Forum schedule + renewal timing maths
├── scheduler.py            change windows and daily-cap leveling
├── discovery.py            TLS scanning and target parsing
├── db.py                   SQLite store
├── vault.py                key sealing and secret references
├── issuers/                ACME (RFC 8555, DNS-01) and the local CA
├── connectors/             files, keystore, f5, fortigate, panos, manual
└── demo.py                 simulated estate for `farrier demo`
tests/                      pytest suite
examples/                   inventory and DNS hook examples
web/                        Next.js app (landing page, dashboard, docs)
└── src/
    ├── app/(marketing)/    landing page
    ├── app/dashboard/      dashboard screens
    ├── app/docs/           these docs (MDX)
    ├── app/api/farrier/      server-side proxy to the Farrier API (+ demo mode)
    ├── components/ui/      primitives: Button, Card, Table, Dialog…
    ├── components/         dashboard, charts, marketing, status vocabulary
    ├── lib/                API client, types, policy port, demo data
    └── proxy.ts            optional Basic auth for the dashboard
```

## Development setup

**Engine**

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
farrier demo
```

**Dashboard**, in a second terminal:

```bash
cd web
npm install
echo "FARRIER_API_URL=http://127.0.0.1:8740" > .env.local
npm run dev
```

Leave `FARRIER_API_URL` unset to work against the built-in demo data.

## Running checks

```bash
python -m pytest                     # engine: unit, end-to-end, ACME and connector tests
cd web && npm run lint && npm run build
```

The engine tests need no network. ACME runs against an in-process RFC 8555 server, and appliance connectors run against mock management APIs (`httpx.MockTransport`). `npm run build` also type-checks and prerenders the docs.

## Conventions

**Python**

- Python 3.11+, type hints, `from __future__ import annotations`.
- Keep dependencies minimal: `cryptography`, `httpx`, `fastapi`, `uvicorn`.
- Engine changes need a test. State-machine changes need an end-to-end test in `tests/test_engine.py`.
- Never log or return secrets or private keys.

**TypeScript / web**

- Components use design tokens, never raw hex. Read the [Design system](/docs/design-system) first.
- Data fetching goes through the hooks in `web/src/lib/api.ts`. The browser only talks to `/api/farrier/*`.
- `web/src/lib/types.ts` mirrors the API in `farrier/api.py`. **If you change an API response, update the types in the same PR**, and update `web/src/lib/demo.ts` so demo mode stays faithful.
- `web/src/lib/policy.ts` is a port of `farrier/policy.py`. Change both together.
- Docs live in `web/src/app/docs/<slug>/page.mdx`. Document every config key, route and state you add.

## Adding a connector

1. Write the class in `farrier/connectors/<kind>.py` following [Writing a connector](/docs/connectors#writing-a-connector), with a module docstring listing its config keys (the API serves it to the dashboard).
2. Register it in `REGISTRY` in `farrier/connectors/__init__.py`.
3. Add tests against a mock transport in `tests/test_appliances.py`: deploy, rollback, and failure mid-deploy.
4. Add a label to `CONNECTOR_LABEL` in `web/src/components/status.tsx`, and a section to `connectors/page.mdx`.
5. Say in the PR whether you tested against real hardware, and which firmware version.

## Pull request checklist

- [ ] `python -m pytest` passes
- [ ] `npm run lint` and `npm run build` pass in `web/`
- [ ] New behaviour has tests
- [ ] API changes are reflected in `web/src/lib/types.ts`, the demo data and the [API reference](/docs/api)
- [ ] New config keys and defaults are documented
- [ ] UI checked in light and dark mode, at mobile width, and with keyboard only
- [ ] No secrets, keys or customer hostnames in code, tests or screenshots

## Reporting security issues

Don't open a public issue. Follow the private process on the [Security](/docs/security#reporting-a-vulnerability) page.
